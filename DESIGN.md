# Design

KA Cosmetology is a server-rendered, single-route brochure site. TanStack Start
loads `/`, Nitro renders it, and React hydrates the same tree. The application
has no general business API/data-service layer: authored business data is
compiled from TypeScript in `src/data/`. The narrow render-time server function
lives in `src/routes/index.tsx`.

## Boundaries and dependency direction

```text
routes -> app -> features/widgets -> components/ui
                  |       |
                  +----> hooks/libs -> data/types
```

Routes own URL/search loading and document metadata. App providers own shared
render/UI state. Features own domain presentation, widgets own page-wide UI,
and `components/ui` stays domain-neutral. Data modules own authored facts and
configuration; libraries own calculations, projections, and external adapters.
Lower layers do not import feature presentation. Path aliases in `tsconfig.json`
make these boundaries visible.

Canonical ownership matters because most changes cross several rendered views:

- `services.ts` owns stable `ServiceId`, catalog names, prices, and categories.
- `servicePriceHistory.ts` owns the immutable, `ServiceId`-keyed price ledger;
  `priceHistory.ts` performs the pure rolling-window calculation.
- `promotion.ts` owns campaigns, applicability, active selection, and
  deterministic non-stacking precedence; `promotionValidation.ts` owns the
  production configuration gate. Evidence: F-001–F-007 and
  `src/data/promotionValidation.test.ts`.
- `business.ts` owns brand, practitioner, locations, contacts, and structured
  opening schedules. UI, JSON-LD, analytics domain, and committed public files
  are projections, not competing sources. Evidence: F-008, F-014,
  `src/data/business.test.ts`, `src/libs/openingHours.test.ts`.
- `navigation.ts` owns labels and section IDs; `useSectionNavigation` owns the
  scroll command, `HomePage` owns deferred mounting, and `UIProvider` observes
  active sections. This distribution separates data, command, mounting, and
  observation rather than creating multiple navigation policies.

## Public interfaces and data flow

The route loader resolves one `RenderTimeSnapshot`; `RenderTimeProvider` gives
SSR and hydrated consumers the same reference instant, then switches live mode
to the browser clock after hydration. A fixed query value is accepted only in
Playwright mode. Promotion and opening-hours consumers receive this shared time.
Evidence: F-010, `src/libs/renderTime.test.ts`,
`src/app/providers/RenderTimeProvider.test.tsx`.

`businessProfile` flows through typed selectors into contact UI,
`toBeautySalonJsonLd`, analytics configuration, and `publicMetadata` renderers.
The generation script writes four committed public files; `pnpm check` and
`pnpm build` compare generated bytes and fail on drift. Evidence: F-008,
`src/libs/publicMetadata.test.ts`, `scripts/generate-public-metadata.mjs`.

Services reference promotions and history by `ServiceId`. Current promotion
resolution and immutable historical facts deliberately remain separate: a new
campaign cannot rewrite what a past customer price was. UI consumes both and
renders the disclosure. Evidence: F-001, F-002, F-004, F-005,
`src/features/services/components/ExpandableServiceCard.test.tsx`.

## State, errors, and background work

`UIProvider` owns menu/scroll/active-section state. `RenderTimeProvider` owns the
render-time boundary. Price history and authored configuration are immutable;
components do not mutate process-wide data during render.

Eager home content renders normally. Below-fold sections mount after load/idle
or direct hash demand, and each is wrapped in its own
`DeferredSectionBoundary`. A rejected lazy chunk therefore replaces only that
section with Polish recovery UI; reload remains user-triggered. Evidence: F-003,
`src/features/home/components/DeferredSectionBoundary.test.tsx`.

`scheduleDeferredWork` owns when optional work starts: analytics after load and
idle, fonts after first scroll or a 4-second fallback. `analytics.ts` alone owns
tracker import/initialization: one initial attempt, one retry only on later
demand, then terminal disablement with static warnings. UI callers remain
fire-and-forget. Evidence: F-012, `src/libs/analytics.test.ts`.

## Key decisions

- Looks wrong at first glance; intentional because historical price rows repeat
  values explicitly. They are materialized business facts, not derivations from
  today's catalog or campaign configuration. Evidence: F-002,
  `src/data/servicePriceHistory.test.ts`.
- Looks wrong at first glance; intentional because multiple active promotions
  are returned before service-level resolution. Different services can receive
  different winners; stacking is forbidden and tie-breaks are deterministic.
  Evidence: F-005, `src/data/promotion.test.ts`.
- Looks wrong at first glance; intentional because the analytics client factory
  is exported with `@internal`. It is the same implementation used by the
  production singleton and permits deterministic lifecycle tests without global
  reset hooks or duplicate state machines. Evidence: F-012,
  `src/libs/analytics.test.ts`.
- Looks wrong at first glance; intentional because Mobile Safari skips only the
  synthetic reload-recovery assertion. WebKit retains the injected rejected
  module; isolation and accessibility still run, while Chromium proves reload
  recovery. Evidence: F-003,
  `tests/e2e/deferred-section-failure.spec.ts`.
- The E2E client-ready document attribute is a test synchronization contract,
  set after React effects install interactive behavior. It is not product state.
  Evidence: F-010, `src/app/providers/RenderTimeProvider.test.tsx`,
  `tests/e2e/pages/HomePage.ts`.

## Change guide

### Local feature

Start in `src/features/<domain>/`; keep local sections/components and co-located
tests there. Reuse `components/ui`, import facts from `data`, and add an E2E page
object only for user-visible behavior. Configuration/schema changes are usually
none. Run focused tests, `pnpm check`, and `pnpm test`. Do not put domain policy
in a generic primitive.

### Multi-module feature

Start at the canonical data or library owner, define the typed interface, then
adapt features/widgets/routes outward. Expected files are the owner, consumers,
co-located tests, and relevant E2E page objects/specs. Update generated public
metadata when business identity changes. Run `pnpm run validate`. Do not create
a second canonical record to avoid a consumer migration.

### Cross-cutting feature

Write an execution plan first. Identify one policy owner, public interfaces,
every consumer, configuration/generation effects, operational checks, and
rollback. Expect tests at each boundary plus production-build E2E where loading,
SSR/hydration, navigation, or readiness changes. Do not add global mutable state,
test-only production branches without a guard, or broad compatibility shims.

## Known debt

- **F-011 — Medium, rejected at plan approval.** Repository evidence does not
  contain deployed-revision lookup, Dokploy/Cloudflare rollback or cache-purge
  procedures, production ownership, or escalation contacts. Consequence: a
  responder can validate locally but cannot complete production recovery from
  repository instructions alone. See [RUNBOOK.md](./RUNBOOK.md).
- **F-016 — Medium, rejected at triage.** One recurring campaign is represented
  as explicit monthly records. Consequence: extending or changing it requires
  synchronized edits and review of repeated copy, although validation protects
  IDs, dates, and catalog references.

The repository contains no registry of out-of-repository consumers. That means
none can be discovered here, not that none exist. Re-check with the relevant
owner before changing exported, DOM, analytics, generated-file, or deployment
contracts.
