## Behavior and diagnostics contract

- Attempt 1 starts on the first guarded `initAnalytics()` or
  `trackPlausibleEvent()` demand. Concurrent demand shares that attempt.
- A failed first import drops pending events, clears the in-flight promise, and
  allows exactly one later-call retry.
- A successful retry initializes once and can forward the event that requested
  the retry. A failed retry disables all later analytics work for that page.
- Any `module.init()` exception disables analytics immediately. The caught
  value is discarded and initialization is never repeated.
- Diagnostics are exact, static, single-argument warnings:
  - `[analytics] Plausible failed to load; one later retry remains.`
  - `[analytics] Plausible failed to load after retry; analytics disabled.`
  - `[analytics] Plausible initialization failed; analytics disabled.`
- No caught value, event, property, URL, endpoint, or user data is logged.
  At most two warnings can occur per page.

## Risks and uncertainty

- Retrying the same failed dynamic import is browser- and failure-mode-dependent;
  this remains bounded best effort, not a delivery guarantee.
- A blocker or policy denial can make both imports fail; analytics then remains
  disabled for that page as designed.
- Events associated with a failed attempt remain lossy because queueing would
  add privacy and lifecycle scope.
- Repository evidence does not establish whether production infrastructure
  collects browser console warnings, so diagnostics improve local inspection
  but are not claimed as alerts or durable logs.
- The Plausible browser build's one-shot initialization behavior remains an
  upgrade-sensitive assumption pinned by terminal init-failure tests.
